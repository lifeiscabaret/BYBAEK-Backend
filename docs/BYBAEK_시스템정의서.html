01

서비스 개요 & 사용자 여정

소상공인 바버샵 사장님의 인스타그램 마케팅을 AI로 완전 자동화하는 B2B SaaS입니다. 사장님은 설정 1회 + 승인 1회만 하면 됩니다.

사장님이 OneDrive에 시술 사진을 올려두면, 백엔드가 이를 자동으로 수집하고, 실시간 헤어 트렌드를 반영해 인스타그램 게시물(캡션·해시태그·CTA)을 자동 생성하고, 설정에 따라 자동 업로드하거나 사장님 검토를 거쳐 발행합니다.

💡 쉬운 설명 — 이 백엔드가 하는 일 한 줄 요약

"사장님의 사진 폴더(OneDrive)를 지켜보다가, 요즘 유행을 검색해서 반영한 인스타 글을 대신 써주고, 정해진 시간에 올려주는 자동 SNS 담당 직원"입니다. 그 '직원'의 두뇌가 바로 AI 에이전트 파이프라인(6장)입니다.

💡 쉬운 설명 — "3계층"이란?

프론트엔드는 사장님이 보는 화면(웹사이트), 백엔드는 화면 뒤에서 실제 일을 처리하는 서버(이 문서의 대상), 데이터/AI/외부 API는 백엔드가 필요할 때 불러 쓰는 창고와 도구들입니다. 백엔드가 가운데서 모든 것을 지휘합니다.

요청 흐름 두 가지

  • 동기(실시간) 흐름 — 사장님이 화면에서 버튼을 누름 → 라우터가 즉시 처리해 응답. 예: 로그인, 온보딩 저장, 사진 조회, custom_chat 실시간 캡션 스트리밍.
  • 비동기(백그라운드) 흐름 — 사람이 없어도 서버가 스스로 실행. 예: 매 정각 스케줄러의 자동 게시물 생성, 4시간마다 OneDrive 동기화, 큐 워커의 사진 다운로드·필터링.

애플리케이션 부팅 순서 main.py

  1. load_dotenv() — 환경변수 로드.
  2. FastAPI(title="BYBAEK API", version="1.0.0", lifespan=lifespan) 생성.
  3. CORS 미들웨어 — localhost:3000 + 환경변수 FRONTEND_URL(콤마 구분 다중) 허용, credentials 허용.
  4. 라우터 8종 등록(각 /api/* prefix).
  5. lifespan 진입 시: APScheduler에 잡 2개 등록 후 scheduler.start(), 이어서 start_worker()로 큐 워커 daemon thread 기동.
  6. GET / 헬스체크: {"status":"ok","service":"BYBAEK API"} (App Service 배포 확인용).
백그라운드 잡주기 (KST)함수동작
자동 게시물 생성매 정각 (minute=0)_check_and_run_schedules모든 샵을 순회하며 업로드 시각·요일·insta_auto_upload_yn=Y 매칭 시 run_pipeline(trigger="auto")
OneDrive 동기화4시간마다 (hour=*/4)_sync_all_shops_onedrive모든 샵의 sync_photos_internal() 호출 (refresh_token 기반)
사진 큐 워커상시 (30초 폴링)start_worker → polling_loopStorage Queue 소비 → 다운로드 → Blob 저장 → 필터 트리거
💡 쉬운 설명 — lifespan / 스케줄러 / 워커

lifespan은 "서버가 켜질 때 한 번, 꺼질 때 한 번 실행되는 준비/정리 코드"입니다. 여기서 스케줄러(정해진 시간에 알람처럼 실행)와 워커(할 일 목록을 계속 지켜보며 처리하는 백그라운드 일꾼)를 켭니다. 덕분에 사장님이 접속하지 않아도 서버가 알아서 사진을 모으고 글을 올립니다.

스케줄 판정 로직 (main.py)

업로드 시각은 DB의 insta_upload_time(예: "07:00 PM")을 24시간제 정각으로 변환해 현재 시각과 비교합니다. 요일은 insta_upload_days(사용자 지정)를 우선 적용하고, 비어 있으면 insta_upload_time_slot("매일"/"주 3회"→월·수·금/"주 1회"→월) 기본값으로 폴백합니다.

인증 모델 주의

라우트에 FastAPI Depends() 가드가 없습니다. 신원은 App Service Easy Auth가 주입하는 헤더(X-MS-CLIENT-PRINCIPAL-ID/NAME, x-ms-token-aad-access-token/-refresh-token)로 흐르며, shop_id = MS principal ID 입니다. auth.py에는 개발용 하드코딩 폴백(test_barber_jiyeon)이 있어 운영 배포 전 제거 검토가 필요합니다(13장).

06

AI 에이전트 파이프라인 (STEP 0–6)

핵심 두뇌입니다. orchestrator_v2.py의 LangGraph StateGraph가 상태(PostState)를 노드에서 노드로 넘기며, 두 개의 품질 게이트(트렌드·캡션)와 재시도·모델 승격·사람 검토 분기를 수행합니다.

💡 쉬운 설명 — StateGraph / 노드 / 게이트

공장의 컨베이어벨트를 떠올리세요. 노드는 각 작업 공정, 상태(PostState)는 벨트 위를 흐르는 작업물 상자입니다. 게이트는 "품질검사대"로, 기준(0.7점) 미달이면 다시 앞 공정으로 돌려보내(재시도) 다시 만들게 합니다. 사람(LangGraph)이 아니라 코드가 이 흐름을 자동으로 지휘합니다.

사용자 로그인은 Entra ID + App Service Easy Auth, 서버-Claude 간은 Managed Identity(AAD 토큰), 외부 SNS는 OAuth 장기토큰으로 3원화되어 있습니다.

이 프로젝트의 대표적 장애 원인 (해결됨)

Foundry의 /anthropic 엔드포인트는 api-key를 거부하고 AAD Bearer 토큰만 받으며, 토큰 audience(scope)가 정확히 https://ai.azure.com/.default여야 합니다. 이를 어기면 401이 나고 post_writer가 목업(가짜) 캡션으로 폴백합니다. 또한 이 앱에는 OneDrive용 AZURE_CLIENT_ID/TENANT_ID/CLIENT_SECRET가 있어 DefaultAzureCredential이 시스템 Managed Identity를 못 찾고 실패하므로, 명시적 체인 ChainedTokenCredential(ManagedIdentityCredential(), AzureCliCredential())을 사용합니다(배포=MI, 로컬=az login).

운영 조건: App Service의 시스템 할당 Managed Identity에 bybaek-foundry의 Cognitive Services User 역할이 부여되어 있어야 합니다.

💡 쉬운 설명 — Managed Identity

서버가 다른 Azure 서비스에 접속할 때, 비밀번호(키)를 코드에 넣는 대신 Azure가 서버에게 발급하는 "사원증"입니다. 키가 유출될 위험이 없고, Azure가 알아서 갱신해 줍니다.

보안 점검 요약

  • 양호 .env·credentials.json·token.json은 .gitignore에 포함되어 git에 추적되지 않음(확인 완료).
  • 양호 Claude는 키가 아닌 Managed Identity 토큰 사용.

배포 & CI/CD

main 브랜치에 push하면 GitHub Actions가 자동으로 App Service에 배포합니다. 배포 대상은 변수로 파라미터화되어 있어, 구독/앱 이전 시 값 두 개만 바꾸면 됩니다.

GitHub Actions 워크플로 .github/workflows/main_bybaek-b.yml

# 트리거: main push 또는 수동(workflow_dispatch)
1. Checkout (actions/checkout@v4)
2. Python 3.11 설정 (actions/setup-python@v5)
3. pip install -r requirements.txt   # 의존성 설치 검증
4. azure/webapps-deploy@v3
     app-name:        ${{ vars.AZURE_WEBAPP_NAME }}          # 현재: bybaek-backend
     publish-profile: ${{ secrets.AZURE_WEBAPP_PUBLISH_PROFILE }}
     package: .
💡 쉬운 설명 — CI/CD와 게시 프로필

CI/CD는 "코드를 올리면(push) 자동으로 서버에 반영되는" 자동 배포 파이프라인입니다. 게시 프로필(publish profile)은 특정 App Service에 배포할 권한이 담긴 자격증명 파일로, GitHub Secrets에 안전하게 보관됩니다.

다른 구독/앱으로 이전하는 법

  1. GitHub → Settings → Variables: AZURE_WEBAPP_NAME을 새 App Service 이름으로 변경.
  2. GitHub → Settings → Secrets: AZURE_WEBAPP_PUBLISH_PROFILE을 새 앱의 게시 프로필(XML)로 교체.
  3. 새 App Service의 구성(환경변수)에 .env.example 항목을 모두 설정.
  4. 새 App Service에 시스템 Managed Identity 켜고 Foundry에 Cognitive Services User 역할 부여(Claude용).
  5. 커스텀 도메인·CORS(FRONTEND_URL) 재설정.
배포 이력 참고 (README 주석)

과거 구독의 URL은 bybaek-b-…koreacentral-01.azurewebsites.net 형태였고, 현재는 개인 구독 rg-bybaek(Korea Central)로 무중단 이전 완료. 복귀가 필요하면 위 변수 두 개와 환경변수를 이전 값으로 되돌리면 됩니다.
